# Milvasoft.BulkExtensions

Bulk insert, update, delete, insert-or-update (upsert), read, truncate and save changes for Entity Framework Core.

| Package | Content |
| --- | --- |
| `Milvasoft.BulkExtensions` | Provider independent core: model mapping, column selection, transactions, generated value read back, `BulkSaveChanges` ordering. |
| `Milvasoft.BulkExtensions.PostgreSql` | PostgreSQL provider (Npgsql). Streams rows with binary `COPY` and runs one set based statement per operation. |

## Setup

Reference `Milvasoft.BulkExtensions.PostgreSql`. That is enough: the provider is found from the EF Core provider in use.
Registering it explicitly is optional and makes the dependency visible:

```csharp
services.AddDbContext<AppDbContext>(o => o.UseNpgsql(connectionString, npgsql => npgsql.UseBulkExtensions()));
```

## Usage

```csharp
using Milvasoft.BulkExtensions;

await context.BulkInsertAsync(products);
await context.BulkInsertAsync(products, c => c.SetOutputIdentity = true);   // ids, defaults, computed values written back

await context.BulkUpdateAsync(products, c => c.PropertiesToInclude = [nameof(Product.Price)]);
await context.BulkDeleteAsync(products);

await context.BulkInsertOrUpdateAsync(products, c =>
{
    c.UpdateByProperties = [nameof(Product.Sku)];          // needs a unique index
    c.PropertiesToExcludeOnUpdate = [nameof(Product.CreatedBy)];
    c.SetOutputIdentity = true;                             // ids of existing and new rows
});

List<Product> found = await context.BulkReadAsync(keys, c => c.UpdateByProperties = [nameof(Product.Sku)]);

await context.TruncateAsync<Product>();

context.AddRange(orders);              // graphs with database generated keys are fine
await context.BulkSaveChangesAsync();  // one statement per table, in foreign key order
```

Every method has a synchronous version and accepts either a `BulkConfig` or an `Action<BulkConfig>`. Methods return the number of affected rows.

### BulkConfig

| Option | Meaning |
| --- | --- |
| `SetOutputIdentity` | Write database generated values back to the entities: identity keys, default values, computed columns, `xmin`. |
| `PropertiesToInclude` / `PropertiesToExclude` | Limit the inserted or updated properties. Owned and complex type properties are written as `Address.City`; `Address` selects all of them. |
| `UpdateByProperties` | Match rows by these properties instead of the primary key (update, upsert, delete, read). |
| `PropertiesToIncludeOnUpdate` / `PropertiesToExcludeOnUpdate` | Upsert only: what to update on existing rows. An empty include list means existing rows are left unchanged. |
| `CommandTimeout` | Seconds. Defaults to the timeout of the context. |

Unknown property names throw `ArgumentException`, so typos do not silently change what is written.

## Behaviour

- **Transactions.** Each call is atomic. Without a transaction one is started inside the execution strategy of the context, so `EnableRetryOnFailure` works. Inside `BeginTransaction` or a `TransactionScope` the call joins it.
- **Generated values.** As in `SaveChanges`: a key or a property with a database default that is left at its CLR default is generated by the database; a set value is written. Client side generators (for example `Guid` keys) run for entities that leave the value unset.
  In an upsert the same rule decides what an existing row gets: a property left at its CLR default is not updated. So `bool IsActive` with default `true` cannot be set to `false` by an upsert; give such properties a sentinel (`HasSentinel`) or make them nullable, as EF Core also recommends.
- **Read back is applied only after success.** A failed or retried call leaves entities, and for `BulkSaveChanges` the change tracker, as they were.
- **Duplicates.** Update and upsert throw when two input entities have the same match values. Delete and read accept duplicates.
- **NULL match values** match no row (SQL `=`): update, delete and read skip such entities, and upsert inserts them.
- **Change tracking.** Bulk operations do not track entities. `BulkSaveChanges` saves tracked changes and accepts them like `SaveChanges`: only modified columns are updated, concurrency tokens (such as `xmin`) are checked, and a row that was not found throws `DbUpdateConcurrencyException`. `BulkRead` runs through EF Core, so query filters and the tracking behaviour of the context apply.
- **Shadow properties.** Read from the change tracker when the entity is tracked, or from the principal when the property is a foreign key and its navigation is set. When neither is possible the column is not updated, so existing data is not overwritten with defaults.
- **Mapping support.** TPH and TPC inheritance, owned types stored in the owner's table, complex types, value converters, composite keys, PostgreSQL enums and arrays. Owned collections are saved by `BulkSaveChanges`.

### Not supported

- TPT inheritance and entity splitting (a type mapped to more than one table), views and SQL query mappings, shared type entity types (property bags) in the direct methods, JSON columns of owned or complex types (throws `NotSupportedException`).
- The direct methods (`BulkUpdate`, `BulkDelete`, ...) do not check concurrency tokens. `SaveChanges` interceptors and events never run.
- `BulkSaveChanges` runs all inserts, then updates, then deletes. Changes that need another order fail with a constraint error: reusing the key or a unique value of a row deleted in the same save, or swapping unique values between rows. It also cannot save tables that refer to each other in a cycle. Use `SaveChanges` for these.
- Upsert read back matches rows by the values the database returns, so case insensitive or blank padded match columns (`citext`, nondeterministic collations, `character(n)`) throw when values are read back.
- `UpdateByProperties` should identify rows uniquely; with non unique values one entity updates or deletes several rows.
- With `EnableRetryOnFailure`, a connection failure while the commit is being acknowledged makes the whole call run again, which can insert rows twice (the same applies to `SaveChanges`).

## Performance

Compared with EFCore.BulkExtensions.PostgreSql 10.0.1 on the same machine, PostgreSQL 17 in Docker, .NET 10 Release build.
The entity has 9 columns (long identity key, strings, decimal, int, bool, timestamptz, uuid) and a unique index.
Values are medians of 3 runs; process CPU time and allocations are stable between runs, wall time depends on the database and disk.

| Scenario | Rows | CPU ms (this / upstream) | Allocated MB (this / upstream) | Wall ms (this / upstream) |
| --- | ---: | ---: | ---: | ---: |
| Insert | 1,000,000 | 3,188 / 3,625 | 258 / 497 | 4,200–6,200 / 4,400–5,800 |
| Insert, read back ids | 100,000 | 1,594 / 2,125 | 44 / 639 | 1,565 / 1,890 |
| Update | 100,000 | 391 / 750 | 34 / 53 | 1,360 / 1,372 |
| Upsert (half new), read back ids | 100,000 | 1,062 / 1,594 | 58 / 633 | 1,781 / 2,616 |
| Delete | 100,000 | 62 / 125 | 8 / 6 | 125 / 194 |
| BulkSaveChanges (inserts) | 100,000 | 3,141 / 3,844 | 372 / 831 | 3,009 / 3,508 |

Rows are streamed to the database without copying them into an intermediate table in memory; memory use grows only by a few references per row
(plus one entry per returned value when values are read back).

## Adding a database provider

1. Create `Milvasoft.BulkExtensions.<Database>` and derive a class from `Milvasoft.BulkExtensions.Infrastructure.BulkProvider`.
   It receives an open connection inside a transaction, the target table, the rows (values already converted) and the columns to match, set or return.
2. Return generated values through `BulkReturning`: `ConsumeInsertedRow(reader, rowIndex)` for inserts and `ConsumeKeyedRow(reader)` for update and upsert.
3. Add an options extension such as `UseBulkExtensions()` that calls `UseBulkProvider<TProvider>()`, and add the EF Core provider name to `BulkProviderResolver` so the provider is found without registration.
4. Copy the PostgreSQL test suite and run it against the new database.
